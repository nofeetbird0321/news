IBM 发布 LLMON：用特殊 token 把指令和数据分开，Granite 4.1 预览模型抵御提示注入

IBM Granite 团队推出面向大模型的标记语言 LLMON 和两个 Granite 4.1 预览模型：结构分隔符改用保留 token，exec 块绑定指令与数据；团队称在 OPI 基准上比所测最好的前沿模型多挡住 47% 的注入攻击，通用能力与 Instruct 版持平，仍是实验性预览。

中文改写

大语言模型靠上下文生成下一批 token。在一段很长的交互里，上下文会塞满各种成分：系统提示、过去的对话轮次、作用于检索文档的指令、工具返回或用户数据、限制输出的要求，以及推理链。IBM Granite 团队在 Hugging Face 博客上指出，这些成分本来有丰富的结构，但大多要么只是隐含在模型里，要么用 JSON 这类并非为大模型设计的格式表达。团队认为，这是大模型（尤其是较小的模型）脆弱、会以意想不到的方式出错的主要原因之一；结构不明确也会被攻击者利用，比如提示注入。

为此，团队开发了 LLMON（LLM Object Notation，读作 “lemon”），一种面向大模型的原生标记语言，用来把结构和语义明确地告诉模型。语义上连贯的成分用有意义的标签标记，标签外面包着保留的特殊 token 分隔符。数据模式（包括嵌套）以因果语言模型不会误解的方式写明。每个块有唯一 ID，可以指向上下文中任意位置的某条指令，并把它绑定到该指令要处理的数据上，类似编程语言里调用函数并传入参数。

团队同时发布了两个基于 Granite 4.1 基础模型、经训练可以读写 LLMON 标记文本的实验性预览模型：granite-4.1-3b-LLMON-preview 和 granite-4.1-8b-LLMON-preview，以及一个 GitHub 仓库，内含处理 LLMON 的工具包和工作流、模板示例。

团队给出的四项用途

  • 抵御间接提示注入。 藏在用户数据里的注入指令，大多会被 LLMON 模型忽略，因为指令和数据是明确分开的。在部分基准上攻击成功率降到接近零，而常规指令微调模型被劫持的概率很高。团队称这是在保持与 Granite 4.1 Instruct 模型相当的通用能力的前提下做到的。
  • 不串味。 每条指令都绑定到它要处理的确切数据，无关段落、旧的对话轮次和工具输出不会被拉进答案。
  • 应用代码里的结构可以被模型利用。 指令、数据和要求都有清楚的标记。可以在 Mellea 里试用，它会自动把大模型调用转成 LLMON，原生支持这种格式。
  • 不用再逼模型遵守 JSON 结构。 团队提供的转换器可以把现有 JSON 无损转成 LLMON；也可以自定义结构和标签，在 LLMON 模型上微调一个 LoRA 来理解它们。

为什么不用 JSON

JSON 是为解析器设计的，不是为因果语言模型设计的。分词器不受语法约束，而结构是靠 {、"、: 这些在普通文本里也会出现的 token 表达的。在模型眼里，文档里的一个引号和结束一个字段的引号是同一个 token。解析器眼中清清楚楚的转义规则，在模型那里只是统计规律。嵌套深度靠数括号来体现，而 Transformer 在这方面已知较弱，跨度越长越明显。

LLMON 是一种类 XML 的标记，它的结构分隔符是保留的特殊 token 而不是字符，因此结构和内容使用词表中互不重叠的部分。标签写在每个片段的开头，片段之间的边界是明确的。嵌套结构在局部写明，模型不必在长跨度上记住层级关系。

考虑到多数团队已有基于 JSON 的流水线，团队提供了转换工具和示例 notebook，可以在 JSON 和 LLMON 之间无损互转。

与对话模板的关系：在角色之外再标出“每一块是什么”

LLMON 不替代对话模板（chat template），它在对话模板之上补充信息。常规对话模板告诉模型哪部分属于哪个角色（system、user、assistant）；LLMON 还告诉模型每个成分是什么意思，以及成分之间在角色内、跨角色的关系。

预览模型自带对话模板，开发者照常构造传给任何对话模型的 messages 列表，再照常调用 apply_chat_template。唯一的区别是，一个轮次可以给自己的各部分命名，并把每部分标为 exec: True 或 False。标为 True 的部分会被绑定进渲染结果底部的 exec 块，这个块写明要执行哪条指令、作用于什么；标为 False 的部分仍会渲染进上下文，但没有任何地方引用它。博客给出的例子是：

messages = [ { "role": "user",
               "instruction": [{ "value": "Write a short paragraph about", "exec": True }],
               "data": [{ "value": "IBM Company", "exec": True }],
               "requirement": [ {"value": "Use less than 10 words", "exec": True},
                                {"value": "Do not use commas", "exec": True}]
             } ]

模型实际收到的是下面这段（为便于阅读加了换行和缩进，模板本身不输出这些）：

<|open|>instr<|:|>»ñ<|close|>Write a short paragraph about<|open_end|>
<|open|>data<|:|>ä¦<|close|>IBM Company<|open_end|>
<|open|>req<|:|>Á¼<|close|>Use less than 10 words<|open_end|>
<|open|>req<|:|>¢¬<|close|>Do not use commas<|open_end|>
<|open|>exec<|:|>ÄÐ<|close|>
    <|open|>exec<|.|>instruction<|close|>instr<|:|>»ñ<|open_end|>
    <|open|>exec<|.|>input<|close|>data<|:|>ä¦<|open_end|>
    <|open|>exec<|.|>requirement<|close|>req<|:|>Á¼<|open_end|>
    <|open|>exec<|.|>requirement<|close|>req<|:|>¢¬<|open_end|>
    <|open|>exec<|.|>output<|close|>assistant<|:|>ãø<|open_end|>
<|open_end|>
<|open|>assistant<|:|>ãø<|close|>

两字符的块 ID 取自一个固定集合，这个分词器把其中每个 ID 都编码成单个 token，所以无论抽到哪个 ID，指向一个块总是只花两个 token。

角色仍然是一个 user 轮次，但它的成分以五个可单独寻址的块进入模型，由第六个块（exec 块）绑在一起。exec 块说的是：对这份数据执行这条指令，满足这两条要求，把答案写进这里指定的块，也就是模型随后填写的那个 assistant 块。按常规模板，这些成分会被拼成一个字符串，模型得自己推断哪部分是任务、哪部分是对象、哪部分是约束。

提示注入测试：比测试过的最好的前沿模型多挡住 47% 的攻击

间接提示注入是把恶意指令藏在数据载荷里的攻击，载荷可能是检索到的文档、工具返回或用户提供的数据。LLMON 的指令与数据分离针对的正是这个问题。

团队把 LLMON 预览模型和若干开源、闭源模型做了对比，评测基准是 OPI，它把注入放进经典 NLP 任务的数据里，并使用多种攻击策略。报告的指标是稳健性，定义为 1 减去攻击成功率，也就是模型没有执行注入指令的攻击占比。

结果显示，所有非 LLMON 模型都高度易受攻击，执行注入指令的概率很高。在这个基准上 LLMON 基本消除了问题：相对团队测试过的最好的前沿模型多挡住 47% 的攻击，相对最好的开源模型多挡住 95%。团队称在其他基准（ASB 和 StruQ）上观察到类似趋势。

这些基准测的是对静态间接提示注入的稳健性，指令与数据分离直接针对这类攻击。在多轮对话中逐步展开的自适应攻击，团队表示还在改进中。

通用能力与 Granite 4.1 Instruct 持平

团队称安全性的提升没有以通用能力为代价：在各类标准基准上，LLMON 模型与 Granite 4.1 Instruct 模型表现相当。

按团队的说法，如果正在试用 Granite 4.1 3B 或 8B，可以直接换成 LLMON 预览版，通用性能应当相近，而对提示注入的抵抗力强得多。不需要转换流水线，像上面的例子那样给轮次的各部分命名（instruction、data、requirement）就够了，自带的对话模板会把它们转成 LLMON 块。LLMON-converters 库更进一步：如果某个部分本身是结构化的，比如一份 JSON 文档，转换后会保留它的结构，变成带类型、可单独寻址的块，而不是一个不透明的字符串。

训练方法：在后训练阶段学会只认 exec 块

模型从 Granite 4.1 基础检查点出发，而不是从已发布的 Instruct 模型出发，因此 LLMON 行为是在后训练中学到的，没有叠加在现有对话格式之上。

LLMON 定义了六个分隔符，用来标记标签的开始和结束，并支持嵌套和锚定；它们作为保留的单个 token 装进分词器。团队把一份常规指令微调语料重新序列化成 LLMON：每个提示成分变成自己的可寻址块，每个轮次带一个执行块，写明运行哪条指令、作用于哪些输入、输出写到哪里。任务构成与普通 Instruct 模型相同（对话、多轮、RAG、工具调用），团队认为这正是基准表现与常规微调模型接近的原因。

此外，团队在数据里加入诱饵指令和诱饵数据块：它们出现在上下文中，但刻意不被绑定，目标输出保持不变。模型由此学会遵循执行块规定的依赖关系，忽略其余部分。之后是强化学习：五个连续的 GRPO 阶段，涵盖多领域推理、RLHF、知识校准和数学，最后是一个 DPO 阶段，使用一千对在线策略（on-policy）偏好样本，样本来自模型自己对注入尝试的回应。

由此形成的权限规则来自这种布局本身，而不是额外加装的护栏：经由执行块到达的指令具有权威性；作为输入到达的内容（数据、文档、工具模式、工具结果）只是要阅读的材料，不是要执行的命令。执行块没有调用的指令和数据片段会被忽略。团队特别说明，这是一种学到的行为，不是强制保证。 想看它在 LLMON 模型注意力层中的表现，可以试用 Hugging Face Spaces 上的 LLMON Attention Visualization。

自定义词表：以 ScienceWorld 为例

LLMON 不绑定固定模式，可以按自己的领域选标签名和结构，再微调一个适配器来读写它们。团队在 ScienceWorld 上做了演示，这是一个文字类基准，智能体一次发出一条命令完成小学科学任务（比如把水烧开），由模拟器打分。

团队定义了一套描述解题规划轨迹结构的词表，标签包括 instr.task.goal、req.planning_policy.rule、data.state.room、data.state.inventory 和 assistant.next_action。他们用这些标签渲染 ScienceWorld 参考解法的每一步，在 LLMON 模型上微调了一个 LoRA。训练后的模型去玩留出的测试局，并用新词表写出下一步动作。这个 notebook 演示了完整流程，从转换参考轨迹、玩测试局，到把适配器与未训练的基础模型对比打分；面向工具调用智能体的例子在另一个 notebook 里。博客没有给出这个 ScienceWorld 实验的分数。

LLMON: An LLM-Native Markup Language, now in Granite 4.1 3B and 8B

LLMs rely on their context to generate the next set of tokens. Over a long trajectory, the context fills with numerous types of components: a system prompt, past conversation turns, instructions that act on retrieved documents, tool responses or user data, requirements constraining the allowed output, and reasoning chains. The context carries a rich structure, most of which is either implicit to the model or encoded in formats such as JSON that were not designed to be digested by LLMs. This is one of the main reasons LLMs, particularly those on the smaller end of the scale, are brittle and sometimes fail in unexpected ways. The lack of explicit structure can also be exploited by attackers, for example, in the form of prompt injections.

To address this, we developed LLMON (LLM Object Notation, pronounced “lemon”), an LLM-native markup language for explicitly communicating structure and semantics to the models. Semantically coherent components are marked with meaningful tags which are wrapped in reserved special-token delimiters. Data schemas, including nesting, are stated in a way that is unambiguous to a causal LLM. Unique IDs make it possible to point to specific instructions, which could reside anywhere in the context, and bind them to the data payloads they should act on, analogous to the way functions are called and arguments are passed to them in programming languages.

Today we are releasing two experimental preview models, derived from Granite 4.1 base models, trained to consume and generate LLMON-marked text: granite-4.1-3b-LLMON-preview and granite-4.1-8b-LLMON-preview. We are also releasing a GitHub repo, which includes a toolkit for working with LLMON and examples of workflows and templates.

What it enables:

  • Indirect prompt injections, hidden in user data, are mostly ignored by LLMON models due to explicit instruction/data separation. For some benchmarks, attack success rates drop to nearly zero, whereas regular instruction-tuned models get hijacked with high probability. This is achieved while maintaining general capability relative to Granite 4.1 Instruct models.
  • Unrelated passages, old chat turns, and tool outputs don’t get pulled into the answer because each instruction is bound to the exact data it applies to.
  • Instructions, data, and requirements are clearly marked so that their structure and meanings at the application’s code level can be leveraged by the model. Try it out in Mellea, which has native LLMON support enabled by automatically LLMONizing its LLM calls.
  • You no longer need to worry about forcing LLMs to observe JSON structure. Use our converters to turn existing JSON into LLMON without loss. You can also define your own structure and associated tags and tune a LoRA on top of the LLMON models to understand it.

Why not JSON?

JSON was designed for parsers, not for causal language models. The tokenizer is not constrained to respect the grammar, and structure is encoded by tokens ({, ", :) that may also appear in normal text. To a model, a quotation mark inside a document and a quotation mark that closes a field are the same token. Escaping rules that are clear to a parser are only statistical patterns to a model. Nesting depth is encoded by counting brackets, which transformers are known to be weak at, especially over long spans.

LLMON, on the other hand, is an XML-like markup whose structural delimiters are reserved special tokens rather than characters, so structure and content use separate parts of the vocabulary. Tags are stated at the beginning of each span, and the boundaries between spans are explicit. Nested structures are stated locally so the model does not need to keep track of the hierarchy over long spans.

Since most teams already have pipelines built around JSON, we created conversion tools and example notebooks that translate JSON to LLMON and back in a lossless manner.

How is LLMON related to chat templates?

LLMON does not replace chat templates; rather, it enriches them. Where regular chat templates tell the model which part belongs to which role (system, user, assistant), LLMON tells it what each component means and how components relate to each other, within and across roles.

The LLMON preview models ship with their own chat template, so you build the same messages list you would pass to any chat model and call apply_chat_template as usual; it renders the LLMON shown below. The only difference is that a turn can now name its parts and mark each one exec: True or False. A part marked True is bound into the exec block at the bottom of the rendered output, which states which instruction to run and what it operates on; a part marked False is still rendered into the context but is referenced by nothing.

messages = [ { "role": "user",
               "instruction": [{ "value": "Write a short paragraph about", "exec": True }],
               "data": [{ "value": "IBM Company", "exec": True }],
               "requirement": [ {"value": "Use less than 10 words", "exec": True},
                                {"value": "Do not use commas", "exec": True}]
             } ]

<|open|>data<|:|>ä¦<|close|>IBM Company<|open_end|>
<|open|>req<|:|>Á¼<|close|>Use less than 10 words<|open_end|>
<|open|>req<|:|>¢¬<|close|>Do not use commas<|open_end|>
<|open|>exec<|:|>ÄÐ<|close|>
    <|open|>exec<|.|>instruction<|close|>instr<|:|>»ñ<|open_end|>
    <|open|>exec<|.|>input<|close|>data<|:|>ä¦<|open_end|>
    <|open|>exec<|.|>requirement<|close|>req<|:|>Á¼<|open_end|>
    <|open|>exec<|.|>requirement<|close|>req<|:|>¢¬<|open_end|>
    <|open|>exec<|.|>output<|close|>assistant<|:|>ãø<|open_end|>
<|open_end|>
<|open|>assistant<|:|>ãø<|close|>

The two-character block IDs are drawn from a fixed set that this tokenizer encodes as single tokens, so addressing a block always costs two tokens regardless of which ID is drawn.

The role is still a single user turn, but its components reach the model as five separate addressable blocks, bound together by a sixth (the exec block) that states: run this instruction, on this data, subject to these two requirements, and put the answer in the block named here, which is the same assistant block the model then fills. A conventional template would have flattened all components into one string and left the model to infer which part was the task, which was the subject, and which were constraints.

How LLMON addresses prompt injection attacks

Indirect prompt injection is a type of attack where a malicious instruction is hidden in a data payload, such as a retrieved document, a tool response, or user-provided data. This is the problem LLMON’s instruction/data separation is designed to address.

We compared the LLMON previews against several open-source and closed-source models. We evaluated on the OPI benchmark, which places the injection in the data of classic NLP tasks. Several attack strategies are employed. We report robustness, defined as 1 − attack success rate: the share of attacks where the model does not carry out the injected instruction.

[Image 1: OPI]

All non-LLMON models are highly susceptible, carrying out the injected instructions with high probability. LLMON practically eliminates the problem on this benchmark, avoiding 47% more attacks relative to the best frontier model that we tested, and 95% more than the best open-source model. We observe similar trends on other benchmarks (ASB and StruQ). It is worth noting that these benchmarks test robustness to static indirect prompt injections. The instruction/data separation directly addresses this type of attack. We are actively working on also improving adaptive attacks which unfold over many chat turns.

General capability

Safety gains don’t come at the expense of general capability. Across standard benchmark categories, the LLMON models perform on par with the Granite 4.1 Instruct models.

[Image 2: Granite-4.1 vs LLMON]

In short, if you’re experimenting with Granite 4.1 3B or 8B today, you can swap in the LLMON preview and should see comparable general performance with much stronger resistance to prompt injection. No conversion pipeline is required. Naming the turn's parts (e.g., instruction, data, requirement as in the example above) is enough. The shipped chat template turns those into LLMON blocks for you. Our LLMON-converters library goes one level deeper: if a part is itself structured, such as a JSON document, LLMONizing it preserves that structure as typed, individually addressable blocks, instead of one opaque string.

How we trained the models

The models start from Granite 4.1 base checkpoints rather than the released instruct models, so LLMON behavior is learned during post-training rather than layered on an existing chat format.

LLMON defines six delimiters that mark the start and end of tags and allow nesting and anchoring; they are installed in the tokenizer as reserved single tokens. We re-serialized a conventional instruction-tuning corpus into LLMON: every prompt component becomes its own addressable block, and each turn carries an execution block naming which instruction to run, which inputs it operates on, and where the output goes. The task mix is the one a normal instruct model sees (chat, multi-turn, RAG, tool calling), which is why benchmark performance stays close to the conventionally tuned model. In addition, we augment the data with decoy instructions and data blocks that are present in context but deliberately left unbound, while the target output is unchanged. So the model learns to follow the dependencies dictated by the execution block and ignore the rest. Reinforcement learning follows: five sequential GRPO stages spanning multi-domain reasoning, RLHF, knowledge calibration, and math, followed by a final DPO stage on a thousand on-policy preference pairs built from the model’s own responses to injection attempts.

The resulting privilege rule falls out of this layout rather than an added guardrail: an instruction reached through an execution block is authoritative, while anything reached as input (data, documents, tool schemas, tool results) is material to read, not a command to follow. Furthermore, instructions and data spans that are not called on in the execution block are ignored. This is a learned behavior, not an enforced guarantee. To see how this plays out in the attention layers of a LLMON model, try the LLMON Attention Visualization on Hugging Face Spaces.

Bring your own vocabulary (ScienceWorld)

LLMON is not tied to a fixed schema: you can choose tag names and structure that fit your domain and fine-tune an adapter to read and write them. We demonstrate this on ScienceWorld, a text-based benchmark where an agent carries out elementary science tasks (such as boiling water) by issuing one command at a time and receiving a score from the simulator. We defined a vocabulary capturing the structure in the planning trajectories involved in solving these tasks. The vocabulary includes tags such as instr.task.goal, req.planning_policy.rule, data.state.room, data.state.inventory and assistant.next_action. We rendered every step of ScienceWorld's reference solutions with these tags and tuned a LoRA on top of a LLMON model. The trained model then plays held-out games and writes its next action in the new vocabulary.
